# JVM 面试题

> 覆盖 JVM 整体架构、运行时数据区、对象模型、GC（含 STW 三色标记）、Class 文件与类加载、JMM、编译优化与执行引擎等高频考点；每题给出深入、全面的标准纯文本描述答案。


### 1、JVM 是什么？为什么 Java 能"一次编译、到处运行"？

JVM（Java Virtual Machine，Java 虚拟机）是 Java 生态的核心，负责把字节码翻译成机器可执行的指令，屏蔽底层操作系统差异。Java 的核心目标是"一次编译、到处运行"（Write Once, Run Anywhere），实现机制是：

- 编译器 `javac` 不直接生成机器码，而是生成与平台无关的**字节码（Bytecode）**，存储在 `.class` 文件中；
- 每种操作系统都有一份对应的 JVM 实现，由 JVM 负责把字节码翻译成该平台的机器指令；
- 对开发者而言，只要源码相同，无论在哪种操作系统上运行，结果一致。

因此 JVM 承担两个角色：**字节码的"翻译器"** 与 **运行时的"管理者"**（管理内存、调度线程、回收垃圾）。"一次编译到处运行"的本质是"源码层面的可移植性 + 运行时的翻译层"：`javac` 产出的 `.class` 与平台无关（只规定指令语义、不绑定具体指令集），各平台 JVM 各自翻译成本地机器码。JVM 不只跑 Java——Kotlin、Scala、Groovy 等只要能编译成合法 JVM 字节码都能跑在上面。


### 2、JVM 的整体架构由哪几部分组成？

JVM 整体架构由**三大子系统 + 一个本地接口**组成：

- **类加载子系统（Class Loader Subsystem）**：把 `.class` 加载进 JVM，并进行验证、准备、解析、初始化；
- **运行时数据区（Runtime Data Area）**：内存划分，含线程共享的方法区、堆 + 线程私有的虚拟机栈、本地方法栈、程序计数器；
- **执行引擎（Execution Engine）**：解释器 + JIT 编译器 + 垃圾回收器，负责翻译并执行字节码、编译热点代码、回收对象；
- **本地方法接口（JNI）**：Java 调用 C/C++ 本地库的桥梁，`native` 方法实现都在 JVM 之外的本地动态链接库。

完整执行链路：`.java → javac → .class → 类加载 → 运行时数据区 → 执行引擎（解释 + JIT）→ 机器码`。


### 3、JVM 的运行时数据区分为哪几块、各自存什么？

JVM 运行时数据区主要分为五块：程序计数器、虚拟机栈、本地方法栈、堆、方法区。JDK 8 后方法区由本地内存中的元空间 Metaspace 取代永久代。

程序计数器记录当前线程正在执行的字节码指令地址，是字节码执行的行号指示器，执行 native 方法时它的值为空。

虚拟机栈每个方法执行时会创建一个栈帧，栈帧内部包含局部变量表（存方法参数和局部变量）、操作数栈（字节码操作的数据中转）、动态链接（指向运行时常量池中方法的引用）和方法返回地址。

本地方法栈与虚拟机栈作用类似，但服务于 native 方法，HotSpot 把两者合二为一。

堆用于存放几乎所有的对象实例和数组，是垃圾回收的主战场，也是 JVM 中最大的一块内存。堆在逻辑上可划分为新生代和老年代（分代收集）。

方法区存放已被加载的类信息（类型信息、字段、方法、常量池）、静态变量、即时编译后的代码缓存等。JDK 8 前用永久代实现，JDK 8 起用元空间，元空间使用本地内存，默认只受系统内存限制，但可配置上限。方法区中的运行时常量池存放编译期生成的字面量和符号引用，是理解 String.intern 和 Class 文件结构的基础。

按线程归属划分：**线程私有**的是程序计数器、虚拟机栈、本地方法栈，随线程生灭；**线程共享**的是堆和方法区，是 GC 和类加载关注的重点。面试加分点是能说清"元空间取代永久代是为了避免永久代大小难以确定、类元数据受堆管理限制、且永久代字符串常量池导致的溢出问题"。


### 4、各类内存溢出分别由什么原因导致、如何排查？

堆溢出 OutOfMemoryError: Java heap space：堆中存活对象过多导致无法分配新对象，常见原因是内存泄漏（对象只增不减）或堆设置过小。排查用 MAT 分析 hprof 快照，看支配树和大对象，定位无法回收的对象引用链。

元空间溢出 OutOfMemoryError: Metaspace（JDK 8 前为 PermGen space）：加载的类过多、动态生成类过多（CGLib/ASM 动态代理、大量 JSP、Groovy 脚本、反射生成类）或元空间上限过小导致。排查关注类加载器的数量是否异常增长，典型场景是类加载器泄漏导致类无法卸载。

直接内存溢出 OutOfMemoryError: Direct buffer memory：NIO 的 ByteBuffer.allocateDirect 分配堆外内存，不归堆和 GC 直接管理（靠虚引用 + Cleaner 回收），频繁分配而未及时释放会导致堆外内存耗尽。排查关注 MaxDirectMemorySize 设置和直接缓冲区使用。

线程数溢出 OutOfMemoryError: unable to create new native thread：本质是 native 内存不足，无法为新的线程分配栈内存。原因可能是创建线程过多未回收、系统进程线程数达到上限（ulimit -u）、或堆外内存耗尽。排查检查线程数、调整 -Xss 减小单线程栈、控制线程池规模。

栈溢出 StackOverflowError：递归过深或方法调用层次过深，线程栈（默认 1M 左右，可由 -Xss 调整）耗尽。排查看堆栈是否出现大量重复的递归帧。

理解各类型溢出的成因和排查方向，能体现对 JVM 内存模型的全貌掌握，这是面试中"线上 OOM 怎么排查"的标准铺垫。


### 5、栈帧由哪几部分组成？局部变量表的 slot 复用为什么会阻碍 GC？

**栈帧四件套**：

- **局部变量表（Local Variables Table）**：存方法参数和局部变量；
- **操作数栈（Operand Stack）**：字节码执行时的临时计算区域（LIFO）；
- **动态链接（Dynamic Linking）**：指向运行时常量池的引用，支持符号引用在运行期解析为直接引用；
- **方法返回地址（Return Address）**：方法结束后回到调用位置继续执行。

局部变量表以**变量槽 slot** 为基本单位：boolean/byte/char/short/int/float/reference 各占 1 个 slot，long/double 占 2 个（不允许单独访问其中一个）；实例方法 slot 0 永远是 this。

**slot 复用阻碍 GC**：当一个变量的作用域结束（离开 `{}` 代码块），它占用的 slot 可以被后续变量覆盖。但只要 slot 里还保留着对象的 reference，这个对象就"可达"、GC 无法回收。典型例子：大数组在代码块内用完、块结束后 `System.gc()` 仍不回收——因为 slot 里的引用没被覆盖。解决思路：用完大对象手动置 null，或尽量缩小变量作用域，本质都是让 slot 尽早失效，减少"假性引用"时间。


### 6、静态变量存放在哪里？

JDK 7 之前，静态变量和类元数据一起存放在方法区（永久代）。**JDK 7 起静态变量被移到 Java 堆**，和 `java.lang.Class` 对象（mirror）放在一起：元空间里的 `InstanceKlass` 只保留字段的元信息（名称、类型、在 mirror 中的偏移量），字段的实际值存放在堆中 mirror 对象末尾预留的存储区。

结论：**JDK 8+ 静态变量在堆中（随 Class 对象），元空间只存类定义元数据**。方法区（元空间）里存的是类型信息、运行时常量池、字段/方法元数据、JIT 代码缓存；"方法区存静态变量"是 JDK 7 以前的旧认知，这是高频易错点。一句话总结：方法区只存"类的定义信息"，而"对象实例、静态变量的值、字符串本体"都在堆里。


### 7、元空间为什么能取代永久代？

永久代（PermGen）有两大痛点：

1. **固定大小易 OOM**：`-XX:PermSize`/`-XX:MaxPermSize` 默认只有 64M/82M，Spring、动态代理、大量 JSP 等场景加载类过多时极易 OOM；
2. **GC 复杂**：永久代位于堆内，要 Full GC 才回收，需要专门的回收调优。

此外 HotSpot 与 JRockit 合并时，JRockit 本身没有永久代概念，必须去掉。于是 JDK 8 用**元空间（Metaspace，本地内存）**取代永久代：

- 使用本地内存，默认只受系统内存限制，大幅缓解类元数据空间不足；
- 类元数据搬出堆，降低堆的回收压力；
- 元空间分三块：**Klass Metaspace**（InstanceKlass 等类元数据）、**Non-Class Metaspace**（常量池、方法字节码、注解）、**Compressed Class Space**（压缩类指针，默认 1G）。

注意：`-XX:MaxMetaspaceSize` 强烈建议设置上限（默认 -1 无上限），否则本地内存耗尽可能被系统 OOM Killer 直接杀进程。排查 `OutOfMemoryError: Metaspace` 先看是否类加载器泄漏，再看是否真的类太多。


### 8、new 一个对象时底层发生了哪些步骤？

对象创建过程分五步：

1. **类加载检查**：遇到 new 指令时先到运行时常量池定位类的符号引用，检查该类是否已加载、解析、初始化，若未加载则先执行类加载。
2. **分配内存**：把一块确定大小的内存从堆中划分给对象；堆规整时用指针碰撞（空闲指针向后移动对象大小），堆不规整时用空闲列表（维护可用内存块列表）；内存分配要解决并发安全，JVM 用 CAS 加失败重试保证原子性，或用 TLAB（线程本地分配缓冲）让各线程在自己的私有缓冲区分配，减少竞争。
3. **初始化零值**：把分配到的内存空间除对象头外全部置零，保证实例字段在不显式赋值时也有默认值。
4. **设置对象头**：写入对象的哈希码（实际是延迟计算的）、GC 分代年龄、锁状态标志、线程持有锁、偏向线程 ID、偏向时间戳，以及指向类元数据的类型指针。
5. **执行构造方法**：按开发者代码执行 `<init>` 初始化字段（先父后子）。


### 9、对象在堆中的内存布局是怎样的？

对象内存布局分三部分：

- **对象头**：HotSpot 中由 Mark Word 和 Klass Pointer 组成，Mark Word 存储对象自身运行时数据（哈希码、GC 年龄、锁状态、偏向信息等），Klass Pointer 指向方法区中的类元数据，HotSpot 默认开启压缩指针把 8 字节类型指针压缩为 4 字节。
- **实例数据**：真正存储的字段，包括父类继承的字段，字段按一定规则排列（父类在前子类在后、同宽字段放一起）以达到紧凑分配。
- **对齐填充**：HotSpot 要求对象地址是 8 字节整数倍，不足时补占位字节，方便寻址和内存管理。

加分点：能说明"压缩指针（CompressedOops）在 64 位 JVM 中把对象引用从 8 字节压到 4 字节、堆不超过 32G 时默认开启""对象头在 32 位是 8 字节、64 位是 16 字节（含类型指针）""数组对象头比普通对象多 4 字节存数组长度""Mark Word 是复用字段，无锁态存哈希码+分代年龄、有锁态存锁记录指针"。


### 10、句柄访问和直接指针访问有什么区别？

Java 程序通过栈上的 reference 操作堆上的对象，reference 到具体对象的定位方式有句柄访问和直接指针两种，主流 HotSpot 采用直接指针访问。

句柄访问：在堆中单独划分一块句柄池，reference 先指向句柄池中的句柄，句柄中分别保存"对象实例数据指针"和"对象类型数据指针"。优点是稳定：对象被 GC 移动（复制、整理）时只需修改句柄中的实例指针，栈上的 reference 不用改，特别适合对象频繁移动的收集器。缺点是两次指针寻址，访问慢一点。

直接指针访问：reference 直接指向对象实例数据，对象实例中再保存类型数据指针。HotSpot 用这种方式，优点是访问快、少一次寻址；缺点是对象移动时所有指向它的 reference 都要同步更新，需要额外的读写屏障配合。

两种方式本质是"时间换空间/稳定"与"空间换时间/速度"的权衡。HotSpot 选择直接指针是因为配合分代收集、对象移动不那么频繁，且访问速度收益更明显。回答时能点出"直接指针需要 GC 移动对象时借助读写屏障或卡表维护引用"是加分项。


### 11、字符串常量池存在哪里、为什么被移到堆中？

字符串常量池（StringTable）在 JDK 7 之前位于方法区的永久代，JDK 7 之后被移动到堆中。移动的原因：永久代回收受限（Full GC 才回收）、空间大小固定易溢出，字符串常量池中大量字符串会导致 PermGen OOM；移到堆后可以被及时回收。StringTable 本质是一个哈希表，默认桶数约 60013，通过 -XX:StringTableSize 调整。


### 12、JVM 如何判断一个对象是否可被回收？

判断对象存活有两种思路。引用计数法：对象维护引用计数器，被引用加一、引用失效减一，为 0 即可回收；优点是判定快、简单，缺点是难以处理循环引用（两个对象互相引用但都不再被外部使用，计数永不为 0），主流 JVM 不采用。可达性分析法：以一组 GC Roots 为起点向下搜索引用链，无法到达的对象即不可达、判定为可回收。HotSpot 采用可达性分析。


### 13、Java 有哪些引用类型、各有什么特点？

Java 的引用类型分四种，强度递减：

- **强引用**：默认的，只要强引用链存在，对象永不回收。
- **软引用 SoftReference**：描述有用但非必需的对象，在系统即将 OOM 前（内存不足时）才会被回收，常用于实现内存敏感缓存；可通过 -XX:SoftRefLRUPolicyMSPerMB 调整存活时间。
- **弱引用 WeakReference**：描述非必需对象，只要发生 GC 就会被回收，常用于 WeakHashMap（键弱引用，防止 key 泄漏）和 ThreadLocal（ThreadLocalMap 的 Entry 弱引用 key）。
- **虚引用 PhantomReference**：最弱，无法通过它取得对象实例，唯一作用是对象被回收时收到系统通知，配合引用队列 ReferenceQueue 管理堆外内存（如 NIO DirectByteBuffer 用 Cleaner 回收直接内存）。


### 14、GC Roots 通常包含哪些？

GC Roots 通常包括：

- 虚拟机栈帧局部变量表引用的对象
- 方法区静态属性引用的对象
- 方法区常量引用的对象
- 本地方法栈 JNI 引用的对象
- 被同步锁 synchronized 持有的对象
- JVM 内部引用（类加载器、基本类型的 Class 对象、常驻的异常对象、系统类加载器）

理解 GC Roots 是理解"为什么局部变量用完了对象就能回收"以及"内存泄漏往往是被静态变量或长生命周期对象意外持有引用"的关键。


### 15、为什么 JDK 已弃用 finalize()？

finalize() 被弃用的根本原因是它不可靠、不可控，其执行机制本身就有严重缺陷：对象要被真正回收需经过至少两次标记——可达性分析发现对象不可达后进行第一次标记并筛选，若对象覆盖了 finalize() 且该方法从未被执行过，则对象被放入低优先级 Finalizer 线程队列异步执行；执行完成后对象才会在下一轮 GC 被真正回收。也就是说 finalize() 不一定被调用，即使被调用时机也完全不确定（JVM 正常退出时都不保证执行完）。若 finalize() 中把 this 重新赋给存活对象引用（复活），对象会逃离本次回收、破坏 GC 语义；且复活后的对象下一次不可达时不会再执行 finalize（只执行一次）。

具体弃用原因：

- 执行时机不确定、可能永远不执行
- 拖慢对象回收（至少多一轮 GC）
- 复活对象破坏 GC 语义、造成状态不一致
- Finalizer 线程若被阻塞会堆积待终结对象导致内存问题
- 存在安全风险

JDK 9 起标记弃用 deprecated，官方推荐用 try-with-resources 管理资源，或用 java.lang.ref.Cleaner 配合虚引用做堆外资源清理。面试中要点：明确"finalize 不可靠、不要用于资源释放"。


### 16、常见的垃圾回收算法有哪些、各自的优缺点是什么？

常见垃圾回收算法有四种，分别针对不同场景。

标记-清除：先标记所有存活对象，再统一清除未标记对象。优点：实现简单。缺点：标记和清除两个阶段效率都不高（对象多时耗时）；清除后产生大量不连续内存碎片，导致大对象分配时找不到连续空间而提前触发下一次 GC。它是基础算法，后续算法都基于它改进。

标记-复制：把可用内存分成大小相等的两块，每次只用一块，GC 时把存活对象复制到另一块，再一次性清空用过的块。优点：实现简单、运行高效、无碎片。缺点：可用内存缩水一半，空间浪费大；对象存活率高时复制成本高。它适合存活率低的新生代。HotSpot 实际不是 1:1 而是按 8:1:1 划分 Eden 和两个 Survivor，每次用 Eden 加一个 Survivor（可用 90%），当 Survivor 放不下时用老年代做分配担保。

标记-整理：标记后把存活对象向内存一端移动，再清理边界外的内存。优点：无碎片。缺点：移动对象要更新所有引用，STW 停顿长。适合存活率高的老年代。


### 17、什么是分代收集、记忆集和卡表的作用是什么？

分代收集是上述算法的组合策略，基于"弱分代假说"（绝大多数对象朝生夕死）和"强分代假说"（熬过多次 GC 的对象更长寿）两个经验假设。新生代用复制算法（对象死得快），老年代用标记-清除或标记-整理（存活率高、移动代价大）。跨代引用用记忆集 Remembered Set 记录"老年代中被新生代引用的区域"，配合卡表 Card Table（把老年代按 512 字节分成卡片，有新生代指向的卡片标记为脏卡）避免 Minor GC 时全堆扫描。


### 18、Minor GC、Major GC、Full GC 有什么区别？

Minor GC（Young GC）指新生代的垃圾回收，只回收 Eden 和 Survivor 区。它发生频繁、速度快，因为新生代对象大多朝生夕死。Minor GC 会触发 STW（Stop The World），但时间短，且现代收集器（如 G1）可并发部分阶段。触发条件是 Eden 空间不足。

Major GC 严格定义指老年代的回收，但在多数资料和实践中与 Full GC 混用。若单独指老年代回收，通常伴随至少一次 Minor GC。

Full GC 指对整个堆（新生代 + 老年代）以及方法区（元空间）的回收，STW 时间最长，对性能影响最大，是优化的重点。触发条件包括：

- 老年代空间不足
- 方法区/元空间空间不足
- 调用 System.gc()（只是建议，是否执行由 JVM 决定，可用 -XX:+DisableExplicitGC 禁用）
- Minor GC 前空间分配担保失败（老年代剩余空间不足以容纳新生代晋升的对象）
- 大对象直接进入老年代导致空间不足
- CMS 收集器在并发收集失败时退化为 Full GC

优化的核心思想：尽量减少 Full GC 次数，让对象在新生代被 Minor GC 回收，避免老年代过快增长。判断指标用 jstat 看 GC 频率、YGC/FGC 次数和耗时。


### 19、新生代的对象在什么情况下会被晋升到老年代？

对象从新生代晋升老年代有四种途径，是理解"老年代为何增长"的关键：

- **年龄阈值晋升**：对象头里记录 GC 分代年龄，每熬过一次 Minor GC 年龄加一，达到阈值（默认 15，由 -XX:MaxTenuringThreshold 调整）时晋升。年龄占 Mark Word 的 4 位，所以上限是 15。
- **动态年龄判定**：为了不浪费 Survivor 空间，若 Survivor 空间中"某个年龄及以下的所有对象"总大小超过 Survivor 空间的一半，则年龄大于等于该年龄的对象直接晋升，不必等到 15。这是 JVM 根据实际存活情况动态调整。
- **大对象直接晋升**：超过 -XX:PretenureSizeThreshold 设置的大对象（如大数组、大字符串）直接在老年代分配，避免在 Eden 和 Survivor 之间反复复制。G1 则用 Humongous Region 专门存放大对象。
- **空间分配担保**：Minor GC 前，若老年代剩余空间不足以容纳新生代所有可能存活的对象，会先检查老年代最大可用连续空间是否大于历次晋升对象的平均大小，若不够则直接触发 Full GC 释放空间。

掌握晋升机制有助于回答"为什么频繁 Minor GC 后老年代爆满""如何调 MaxTenuringThreshold"等调优问题。


### 20、什么是 STW？并发标记为什么会漏标、如何解决？

**STW（Stop The World）**：JVM 在执行某些操作（最典型是 GC）时暂停所有应用线程，拿到一份一致性内存快照。可达性分析必须 STW 枚举 GC Roots，所以 STW 不可避免，优化方向是"把更多工作移到并发"而不是"消除 STW"。

**三色标记**：把对象按访问进度涂三色——白色（未访问）、灰色（已访问但字段未扫完）、黑色（已访问且字段扫完）。核心是**三色不变式：黑色对象不能直接指向白色对象**，一旦违背就会漏标。

**漏标的两个必要条件**（Wilson 1994，必须同时满足才漏标）：

1. 应用线程插入了一条"黑色对象 → 白色对象"的新引用；
2. 应用线程删除了所有"灰色对象 → 该白色对象"的旧引用。

解决思路就是破坏两个条件之一，对应两种写屏障（JIT 在引用赋值处自动插入）：

- **增量更新（Incremental Update）**：破坏条件①，黑色对象新增对白色引用时把黑色"反悔"为灰色，最终标记阶段重扫。CMS 用，代价是写屏障开销大。
- **SATB（Snapshot At The Beginning）**：破坏条件②，删除灰色→白色的旧引用时记录旧值、把被删对象标灰，保住快照中的存活对象。G1 用，代价是产生浮动垃圾（本轮保住的不可达对象下轮才回收）。


### 21、Class 文件的结构是怎样的？

Class 文件是一组以 8 位字节为单位的二进制流，各数据项严格按顺序紧凑排列、无分隔符。基础数据类型用无符号整数 u1/u2/u4 表示。整体结构按出现顺序：

- **魔数 magic（u4）**：固定 0xCAFEBABE，标识 class 文件，不符抛 ClassFormatError；
- **版本号（u2+u2）**：次版本 + 主版本，低版本 JVM 无法加载高版本（报 UnsupportedClassVersionError）；
- **常量池（u2 + cp_info[]）**：字面量 + 符号引用，最复杂的部分；
- **访问标志 access_flags（u2）**：public/final/interface/abstract 等；
- **类索引 this_class、父类索引 super_class、接口索引集合**：指向常量池 CONSTANT_Class；
- **字段表 field_info[]、方法表 method_info[]（含 `<init>`/`<clinit>`）、属性表 attribute_info[]**（Code/LineNumberTable 等）。

方法的核心是 Code 属性，内含 max_stack（操作数栈深度）、max_locals（局部变量槽位）、字节码指令流、异常处理表。理解 Class 文件结构是掌握字节码工程（ASM/Javassist）的基础。


### 22、类的完整生命周期有哪些阶段？

类的生命周期分加载、验证、准备、解析、初始化、使用、卸载七个阶段，其中加载、验证、准备、初始化、卸载的顺序固定，解析阶段可在初始化之后开始（以支持运行期动态绑定）。

加载阶段把类的字节码读入内存，在方法区生成对应的 Class 对象。验证阶段确保字节码符合 JVM 规范、不危害 JVM 安全（文件格式、元数据、字节码、符号引用四个层面的校验）。准备阶段为静态变量分配内存并赋零值（如 int 赋 0、引用赋 null，不赋用户指定值；但 static final 常量会直接赋编译期确定的值）。解析阶段把符号引用替换为直接引用。初始化阶段才真正执行静态变量赋值和静态代码块（clinit 方法），这是执行类构造器 `<clinit>` 的过程。


### 23、`<clinit>()` 和 `<init>()` 有什么区别？

| 维度 | `<clinit>()` 类构造器 | `<init>()` 实例构造器 |
| --- | --- | --- |
| 触发方 | 类初始化阶段 | 实例创建（new/反射 newInstance/clone/反序列化） |
| 执行次数 | 每个类仅 1 次 | 每个实例 1 次 |
| 线程安全 | JVM 加锁保证（多线程只执行一次） | 不加锁 |
| 收集内容 | 所有 static 赋值 + static{} 块，按源码顺序 | 实例变量赋值 + {} 块 + 构造器方法体 |
| 父级优先 | 父类 clinit 先于子类 | 构造器首行隐式 super() |

`<clinit>()` 的线程安全代价是可能**死锁**（A 的 clinit 依赖 B、B 又依赖 A 形成初始化环），且 clinit 里有耗时操作会让其他线程永久阻塞——排查时看线程栈的 clinit 帧。若类没有 static 赋值和 static 块，编译器不生成 clinit。


### 24、什么是双亲委派模型？

双亲委派模型：类加载器收到加载请求时，先委派给父加载器尝试加载，父加载器加载不了才自己加载，形成"自底向上委派、自顶向下加载"。标准 Java 层级是 Bootstrap ClassLoader（加载 jre/lib 核心库，C++ 实现）→ Extension ClassLoader（扩展目录）→ Application ClassLoader（应用 classpath）。

为什么要有双亲委派：一是保证同一个类在 JVM 中只被加载一次，避免重复加载造成混乱；二是保证核心 API 安全，无论用户如何自定义 java.lang.String，都会因核心库已被 Bootstrap 加载而无法替换，防止核心类被篡改。这也是"为什么自定义 ClassLoader 通常要打破双亲委派（如 SPI、热部署）"的反向考点。注意 Bootstrap 是 C++ 实现、没有 Java 对象，所以 `String.class.getClassLoader()` 返回 null。


### 25、类在什么时机会被初始化（主动引用）？

类的初始化指执行静态变量赋值和静态代码块（clinit），只发生在"主动引用"时。主动引用主要有六种：

1. 遇到 new、getstatic、putstatic、invokestatic 四条字节码指令且类未初始化时
2. 使用反射调用类时
3. 初始化一个类时若父类未初始化则先初始化父类（但接口不要求先初始化其父接口）
4. 虚拟机启动时初始化包含 main 方法的主类
5. JDK 7 动态语言支持遇到 MethodHandle 解析结果为常量句柄时
6. 接口中定义了 default 方法，其实现类被初始化时


### 26、Java 的类加载器有哪几种？

Java 标准类加载器自上而下：Bootstrap ClassLoader（C++ 实现，加载 jre/lib 下核心库如 rt.jar）、Extension ClassLoader（加载 lib/ext 扩展目录，JDK 9 起被平台类加载器取代）、Application ClassLoader（加载应用 classpath）。开发者可继承 ClassLoader 自定义加载器，通常重写 findClass（推荐）或 loadClass（破坏双亲委派）。


### 27、两个类"相等"的判定条件是什么？

JVM 中判定两个类是否"相等"（用 == 或 instanceof），不仅要求**全限定名相同**，还要求**加载它们的 ClassLoader 必须相同**。即使两个类来源于完全相同的 .class 文件，只要被不同的 ClassLoader 加载，JVM 就认为它们是两个独立的类（`c1 == c2` 为 false）。每个 ClassLoader 实例有独立的命名空间，父加载器加载的类对子可见、子对父不可见、同级兄弟之间互不可见——这是 Tomcat、OSGi 实现类隔离的基础。


### 28、类卸载需要满足什么条件？

类卸载需要三个条件**全部满足**：

1. 该类的所有实例都已被 GC 回收（堆中不存在该类的任何对象）；
2. 加载该类的 ClassLoader 实例本身已被 GC 回收；
3. 该类的 java.lang.Class 对象没有被任何地方引用（无反射持有）。

因此 **Bootstrap/Extension/Application 这些内置 ClassLoader 加载的类永远不会被卸载**（因为加载器本身不回收），只有**自定义 ClassLoader 加载的类**才有机会卸载。类卸载发生在元空间的 GC（Full GC）过程中，用于释放元空间内存。典型场景：Tomcat 热部署、OSGi、Spring DevTools 等动态加载/卸载类的容器。


### 29、Android 的类加载器体系是怎样的？

Android 类加载器同样遵循双亲委派，但加载对象是 Dex 文件：BootClassLoader 加载 Framework 层类；PathClassLoader 加载已安装 APK 的 Dex，是应用的默认类加载器；DexClassLoader 可加载任意路径的 Dex/Jar，本质与 PathClassLoader 相同，只是可以指定优化目录（optDir）。Android 用 multidex 分包突破单 dex 65536 方法数限制（Dex 文件用 16 位索引存方法编号）。


### 30、类加载机制与热修复、插件化有什么关系？

热修复和插件化核心就是类加载机制。QZone 方案把补丁 Dex 插入 PathClassLoader 的 dexElements 数组最前面，让补丁类先被加载实现替换（类加载是按 dexElements 顺序查找的）。Tinker 编译期为每个方法插入探针 + 运行时替换整个 dexElements，实现全量热修。AndFix/Sophix 在 native 层直接替换方法指针（ArtMethod），绕过类加载器。插件化（VirtualAPK、Shadow）用 DexClassLoader 加载插件 APK 的类，再 Hook ActivityThread 的类加载、占坑/插桩绕过系统对四大组件的注册校验，实现动态加载未安装的 APK。要点是理解"类加载顺序决定谁生效"以及"绕过双亲委派"在热修/插件中的运用。


### 31、什么是 JMM？

JMM（Java Memory Model）是一套规范，定义主内存与线程工作内存的抽象关系，以及线程间通过主内存交互的规则，用于屏蔽不同硬件和操作系统的内存访问差异，提供跨平台一致的并发语义。主内存是所有线程共享的内存，工作内存是每个线程私有的（对应 CPU 缓存/寄存器），变量必须先在工作内存操作再同步回主内存，因此产生可见性问题。


### 32、JVM 有哪些方法调用指令？静态分派和动态分派有什么区别？

字节码层面方法调用共 5 条指令：

- `invokestatic`：静态方法，静态链接（编译期定目标）；
- `invokespecial`：构造器、private 方法、super 调用，静态链接；
- `invokevirtual`：虚方法（可被重写的实例方法），动态链接，靠 vtable；
- `invokeinterface`：接口方法，动态链接，靠 itable；
- `invokedynamic`：引导方法 BSM 绑定 CallSite，动态语言/Lambda 用。

**分派区别**：

- **静态分派 = 重载（Overload）**：编译期根据参数的静态类型决定调哪个版本，对应 invokestatic/invokespecial；
- **动态分派 = 重写（Override）**：运行期根据对象实际类型决定版本，对应 invokevirtual/invokeinterface。

动态分派的实现是**虚方法表 vtable**：每个类维护一张，子类重写父类方法就用子类实现覆盖同一下标入口；调用时通过对象 Klass Pointer 找到实际类、再按下标定位方法。itable 按接口组织、需"接口偏移 + 方法偏移"两级定位，所以 invokeinterface 一般比 invokevirtual 略慢（现代 JVM 靠内联缓存优化）。这正是"动态链接"名称的由来——下标编译期确定、入口地址运行期才绑定。


### 33、对象一定分配在堆上吗、什么是逃逸分析？

对象默认分配在堆上，但通过逃逸分析可在满足条件时优化到栈上。逃逸分析分析对象的动态作用域：如果对象在方法内创建且不会被外部引用（不逃逸出方法，如不返回、不赋给静态变量、不传入外部），就可以栈上分配，对象随栈帧销毁自动回收，减轻 GC 压力。逃逸分析是 JIT 编译期的优化，JDK 6 起默认开启（-XX:+DoEscapeAnalysis）。

回答加分点：能说明"逃逸分析不是每次必生效，取决于对象是否真正逃逸""栈上分配不是 JVM 规范要求而是 HotSpot 优化"。


### 34、什么是标量替换、锁消除、TLAB？

基于逃逸分析的两项优化。标量替换：把不会逃逸的对象拆成多个基本类型标量（字段），直接在栈帧分配，进一步减少堆对象。锁消除：如果对象不会被其他线程访问（线程私有无竞争），编译器可去掉对它的同步锁，消除无意义的锁开销。

TLAB（Thread Local Allocation Buffer）：线程本地的分配缓冲，每个线程在 Eden 区预分配一小块私有内存，分配对象时优先在 TLAB 内用指针碰撞快速完成，避免多线程竞争同一块内存的加锁开销；TLAB 耗尽后再向 Eden 申请新块（可能触发 Minor GC）。-XX:+UseTLAB 默认开启，-XX:TLABSize 调整大小。TLAB 是对象分配高效的关键机制。

回答加分点：能说明"TLAB 属于 Eden 的一部分，不是独立空间"。


### 35、什么是 JIT 即时编译、解释执行和编译执行有什么区别？

JIT（Just-In-Time）即时编译是运行时把热点字节码编译为本地机器码的技术，与解释执行配合。解释执行逐条翻译字节码，启动快、占用少但运行慢；编译执行把字节码编译为机器码，运行快但编译有开销。JVM 采用混合模式：启动时先解释执行，通过方法调用计数器 + 回边计数器识别热点代码（热点是方法调用次数多或循环回边多），对热点用 C1（客户端编译器，编译快、优化浅）或 C2（服务端编译器，编译慢、优化深）编译；分层编译让 C1 和 C2 协作，先用 C1 快速编译、热度继续升高再交给 C2 深度优化，兼顾启动和峰值性能。


### 36、Android ART 的编译模式经历了怎样的演进？

Android 侧，Dalvik 使用解释器 + JIT（每应用独立虚拟机、Trace 级 JIT）。ART 取代 Dalvik 后最初用 AOT（Ahead-Of-Time），安装时把字节码全量编译为机器码（oat 文件），运行时零编译、性能提升，但安装慢、占用空间大（APK 体积与 oat 翻倍）。Android 7 起改为 AOT + JIT + Profile 引导的混合编译：运行时 JIT 收集热点，空闲时根据 Profile（记录热点方法）把热点 AOT 编译，兼顾安装速度、启动速度、空间占用和运行性能。理解这条演进线体现对"编译时机（安装期 vs 运行期）"在移动端权衡的把握。

> 附：高频速记 —— JVM 跨平台靠字节码 + 各平台翻译；JDK=JRE+工具、JRE=JVM+类库；三大件=类加载+运行时数据区+执行引擎；堆线程共享、栈线程私有；可达性分析判活、引用链断开即回收；新生代复制、老年代标记整理；双亲委派防篡改保唯一；Minor GC 频繁、Full GC 要少；finalize 不可靠、资源用 try-with-resources/Cleaner；Class 文件魔数 CAFEBABE；clinit 类一次、init 每实例；静态变量 JDK7+ 随 Class 对象入堆；栈帧四件套、slot 复用阻碍 GC；重载静态分派、重写动态分派查 vtable；STW 三色标记、SATB/增量更新防漏标；元空间本地内存取代永久代。
